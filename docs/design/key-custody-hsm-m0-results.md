# Key custody HSM: M0 spike results

Design: `key-custody-hsm.md` section 8 (M0). Env: SoftHSMv2 2.6.1-2.1 (debian bookworm, arm64, Docker Desktop VM, 11 CPUs, token in file backend), Go 1.26.0, `miekg/pkcs11` v1.1.1/v1.1.2. All spikes ran in throwaway containers; scratch code lives outside the repo. SoftHSM is a software token: timings and lockout behaviour say nothing about a real HSM.

| Spike | Result | Consequence for the design |
|---|---|---|
| (a) KEK wrap, GCM | **Works.** `CKM_AES_KEY_WRAP`, `CKM_AES_KEY_WRAP_PAD` (both 32 B DEK -> 40 B), `CKM_AES_GCM` with AAD (128-bit tag), unwrap into a non-extractable session key then GCM decrypt: all OK, DEK bytes round-trip. Wrong AAD and flipped ciphertext bit are rejected (`CKR_GENERAL_ERROR`, not a typed error). Non-extractable KEK cannot wrap itself (`CKR_KEY_UNEXTRACTABLE`) or be read. DEK generated inside the HSM as `SENSITIVE+EXTRACTABLE` session key can be wrapped but not read. RSA-3072 OAEP: only SHA-1 works (SHA-256 params give `CKR_ARGUMENTS_BAD`); wrap/unwrap round-trips. | P1 is supported. Unwrap template must not contain `CKA_VALUE_LEN` (`CKR_ATTRIBUTE_READ_ONLY`). Seal path: generate DEK in HSM, wrap, GCM-encrypt in HSM, destroy. HSM accepts a **zero-length GCM IV** and does not generate IVs: `hsm-gateway` must supply and enforce a random 96-bit nonce. Map `CKR_GENERAL_ERROR` on decrypt to "authentication failed" explicitly. F2 would be OAEP-SHA1 only. |
| (b) concurrent sign, 10 000 sigs | Zero errors in all pooled runs. Debian, session per goroutine: 1 g 4.8k sig/s p99 0.23 ms; 4 g 17-18k sig/s p99 0.4-0.5 ms; **16 g 19-21k sig/s p99 3.7-5.2 ms** (max 8-19 ms, 4 runs). 16 g over a 4-session pool: 15-17k sig/s p99 1.1-1.8 ms. One shared session behind a mutex: 4.4-4.7k sig/s. **One shared session without a mutex: SIGSEGV inside libsofthsm2 (process dies).** 100 000 sessions opened without a limit. Login state is token-wide (second `C_Login` returns `CKR_USER_ALREADY_LOGGED_IN`). | Hot signing is nowhere near a bottleneck. Session pool must make "one operation per session at a time" structurally impossible (checkout/return, no shared handle); a test must cover it, because misuse is a crash, not an error. Pool of ~4 is enough and has the best tail. Treat `C_Login` as once per process, not per session; a logout anywhere logs out all sessions. |
| (c) r\|\|s, low-s, recovery | 10 000/10 000 digests recovered the expected address (debian and alpine, `crypto.SigToPub` and `VerifySignature`). Output always 64 B. **~49.7% of raw signatures have high s** (4967, 5066, 4963 in three runs); recid split 50/50. | Low-s normalisation is mandatory, not defensive. Recovery-id search over {0,1} is sufficient. Property test as planned in M2. |
| (d) at rest | Imported AES key with known bytes: **plaintext found in the token file when `CKA_PRIVATE=false`**, even with `CKA_SENSITIVE=true`. With `CKA_PRIVATE=true` (also when `SENSITIVE=false`) the value and label are not present in any file (file objects 771 B vs 682 B plaintext). SoftHSM defaults generated secret keys to `PRIVATE=true`, `SENSITIVE=false`, `EXTRACTABLE=false`. | KEK/Hot Key templates must set `CKA_PRIVATE=true` explicitly and `hsm-gateway` self-test must read it back and refuse otherwise. `CKA_SENSITIVE` alone gives no at-rest protection. I did not prove the encryption key is derived from the PIN (no offline decryption attempted); SoftHSM documents it, not verified here. |
| (e) wrong PINs | **No lockout.** 100 wrong user PINs across fresh sessions: still `CKR_PIN_INCORRECT`, `CKF_USER_PIN_LOCKED` never set, `FINAL_TRY` never set (`COUNT_LOW` is set from the first attempt), correct PIN works afterwards, SO `C_InitPIN` also works. | Offline PIN brute force and online guessing are not rate-limited by SoftHSM. The PIN is only as strong as the secret file plus host access; `hsm-gateway` must rate-limit and alert on login failures itself. Lockout behaviour must be re-tested on the real HSM. |
| (f) binding | `miekg/pkcs11`: BSD-3, v1.1.2 (2026-01-22), commits to 2026-08, low-level, exposes wrap/unwrap/GCM/EC params. Builds and passes (c)(b) on debian (glibc) and alpine (musl, needs `build-base libtool`); alpine is slower (16 g: 8.7k sig/s, p99 9.7 ms). `ThalesGroup/crypto11`: MIT, thin layer over miekg, but **no secp256k1 (`unsupported elliptic curve`), no wrap/unwrap API**, ECDSA returns DER. Tagged v1.6.8 on the ThalesGroup path declares module path `eclipse-keypont/crypto11` (does not resolve under the old path); project moved and is shipping v2 release candidates. | **Use `miekg/pkcs11`.** crypto11 cannot do the Hot Key (secp256k1) or the KEK. Pin the exact version and vendor; build `hsm-gateway` on debian-slim (distroless-cc acceptable), not alpine. |
| (g) hdkeychain | `hdkeychain` + `btcec` match `go-ethereum-hdwallet` for fresh 24-word mnemonic, indexes 0-1000 (1001/1001), both private derivation and **xpub-only (public) derivation from m/44'/60'/0'/0**. `Zero()` clears `key` and `chainCode` of that `ExtendedKey` only; `Derive` on a zeroed key errors. It does **not** cover: every derived child/intermediate key (each has its own copy), the `*btcec.PrivateKey` from `ECPrivKey()` (needs its own `Zero()`), the `bip39` seed `[]byte`, any `String()` output, or the mnemonic (immutable Go string, cannot be wiped). | M3a xpub issuance is viable. `sweep-signer` must zero each child, each `PrivateKey`, and the seed explicitly; "no mnemonic string on this path" must be enforced by never creating one (feed the seed bytes, do not round-trip through a string). `Zero()` is best effort; Go GC copies are not covered. |
| (h) vm3 | Not run (no remote access). | Operator check on vm3: swap + ptrace_scope. |

## Gate verdict

**P1 (KEK in the HSM, AES-GCM decrypt inside the HSM) is workable on SoftHSMv2 2.6.1. No fallback needed: F1, F2 and F3 are not triggered.** (a) passes for AES wrap, AES-GCM and the unwrapped-key path; RSA-OAEP (SHA-1 only) remains available as F2. Conditions that change the build: explicit `CKA_PRIVATE=true`; gateway-owned GCM nonce; a structurally enforced session-per-operation pool; gateway-side PIN-attempt limiting; mandatory low-s.

## Unverified

- vm3 swap and `ptrace_scope` (operator check on vm3).
- Behaviour on a real HSM (mechanism set, lockout, IV handling, throughput); all numbers are SoftHSM in a Docker VM on arm64, not amd64 or the dev VMs.
- That the at-rest encryption key is derived from the PIN (only observed that private objects are not in plaintext).
- Wrap behaviour after token re-init or SoftHSM upgrade (KEK survival across restarts was not tested beyond one process).
- `hdkeychain` against the repo's real mnemonic/indexes (throwaway mnemonic used, per instruction); memory remanence after `Zero()` (not scanned in a core dump).
- crypto11 v2 rc behaviour (not evaluated; only v1.6.7 built and tested, v1.6.8 inspected as source).
